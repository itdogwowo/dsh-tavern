# 回覆格式的框架標準（**這一頁是契約，不是說明**）

> 模型 → 節點樹 → 消費者（畫面、語音、統計、之後的 workflow）。
> 任何一層要改，先回來改這一頁，再改程式。
>
> 已經釘住它的測試：`test-client.mjs` §4j。
> 解析器的實作在 `lib/client.js`（`parseMessage`）；
> 想貼一段文字看結果：`node parse-preview.mjs`。

## 0. 四個不變量（違反的話，後面的設計全部要重來）

| # | 不變量 | 為什麼 |
|---|---|---|
| **I1** | **模型不吐 HTML、不吐 JSON**（敘事裡）。它寫的還是普通小說 | 格式是**附帶的**，內容才是價值。JSON／HTML 壞一個字元就毀掉整則訊息，而且那些括號與跳脫每回合都要重付 token |
| **I2** | **`.jsonl` 只存原文**，一個字都不改 | 資料可攜（SillyTavern 讀得懂）、可重寫、改規則時歷史會跟著重畫 |
| **I3** | **解析只發生在渲染期** | 規則改了，歷史訊息一起變。存下解析結果等於把規則寫進資料 |
| **I4** | 每個節點都帶 **`source`**（怎麼判斷出來的） | 推斷一定會出錯。錯了要看得出來、要能只讓它影響樣式而不是語音 |

**I1 的例外**：資料區塊的**內容**可以是結構化的（`key: value`），因為那個區塊短、獨立、壞掉只損失那一塊——見 §3。

## 1. 模型可以吐什麼（**主線是乙，甲是安全網**）

| | 形狀 | 成本 | 什麼時候用 |
|---|---|---|---|
| **乙、結構化（主線）** | **一行一個物件**：`{"kind":"speech","who":"老闆娘","text":"你終於來了。"}` | 每行約 30 字元 | 要精確時：`who` 要可靠、語音要選聲音、資料要拆欄位 |
| **甲、純文字（安全網）** | 就是小說。`「…」` 是台詞、`（…）` 是動作 | **零** | 走樣、舊訊息、沒設定時 |
| 丙、標記（選用） | `<名字>…</名字>`（可帶 `who="…"`） | 幾個字元 | 喜歡這個寫法的人 |

**兩者可以混用**：同一則訊息裡是結構化的行就走乙、不是的就走甲。

### ⚠️ 乙為什麼是「一行一個物件」而不是一個大陣列

三個理由，全部是為了**修復**：

1. **一行壞掉只損失那一行**。大陣列是結構性的——少一個括號整包不合法。
2. **修復的單位就是那一行**。「只送壞掉的那一段」才做得到（見 §5.1）。
3. **串流時一行完成就能畫**，不必等整包收完。

**模型只給三件**：`kind`、`who`（可省略）、`text`。
`source`／`para`／`rows` 由**後處理**填——那三件它不需要知道，也不該知道。

### 甲為什麼一定要留著

- **既有資料**：三個月前的對話沒有結構，不該因此讀不出來。
- **走樣是常態**：長對話裡模型會逐渐忘記吐結構（它模仿自己最近的輸出）。那時候畫面退回推斷，**小說還在**。
- **它是安全網**：修復層失敗時的最終退路。

> ⚠️ **看得出來「想」吐結構但壞掉的行，不可以跑推斷。**
> JSON 行裡的引號是**語法**，不是台詞——實測踩過：一行少了大括號的 JSON
> 被推斷層碎成十幾個片段（`{`、`"kind"`、`:`…），那比壞掉本身更難看。
> 這種行降級成**一個**旁白節點，並回報 `bad-json`。

## 2. 顯示語意：`kind` 清單（**固定，不能自己發明**）

這一層是**給讀者與畫面**的語意。要加就往這張表加一列，那是一個有意識的決定。

| kind | 是什麼 | 語音預設 | 能不能推斷 |
|---|---|---|---|
| `speech` | 角色說出來的話 | **唸** | ✅ `「…」` |
| `narration` | 旁白／描寫 | 不唸 | ✅ 其餘 |
| `action` | 動作／舞台指示 | 不唸 | ✅ `（…）` |
| `thought` | 內心／獨白 | 不唸 | ❌ **只走標記**（中文沒有可靠的心聲排版慣例） |
| `panel` | 帶標題的區塊 | 不唸 | ❌ 只走標記 |
| `data` | `key: value` 的列（`rows`） | 不唸 | ✅ 標記內全部符合時 |
| `title` | 標題 | 不唸 | ❌ 只走標記 |
| `choices` | 可選項清單 | 不唸 | ❌ 只走標記 |
| `blank` | 空行（保留段落感） | 不唸 | ✅ |

> ⚠️ **這一層不是引擎語意。** 遊戲要的「意圖／結果／狀態變化」是**另一層**（見 §7）——
> 同一個節點可以兩者都有，但**不要混成一套詞彙表**。

## 3. 節點形狀（parser 與消費者之間的介面）

```js
{
  kind: 'speech' | 'narration' | 'action' | 'thought' | 'panel' | 'data' | 'title' | 'choices' | 'blank',
  source: 'marked' | 'quoted' | 'plain',   // 怎麼判斷出來的（I4）
  who: '',            // 誰說的（標記帶的優先，否則＝這一則訊息的預設角色）
  text: '',           // **原文**，一字不動（不前處理 → 可複製、可搜尋、可逆）
  rows: null,         // 只有資料區塊才有：[{ key, value }]
  para: 0,            // 顯示段落的編號（同一行的片段共用；渲染端據此分組）
  tag: ''             // 只有標記節點才有（使用者宣告的名字）
}
```

> ⚠️ **`para` 不是原文行號。** 一個多行的標記區塊只佔一個 `para`，
> 所以它跟原文行號會**越差越多**。要定位請用 `problems[].line`（見 §5）。

**三個刻意的性質**：

- **`text` 永遠是原文**：不前處理、不剝引號、不加括號。要改外觀由 CSS 做。
- **`para` 是給渲染端的**：同一行的多個片段（台詞＋旁白＋台詞）共用編號，
  消費者不必自己分組。
- **`rows` 出現時 `text` 還在**：不懂 `rows` 的消費者照樣畫得出東西（漸進增強）。

## 4. 判定順序（順序不能換）

```
① 已宣告的標記 → 切出區塊（source = 'marked'）
② 其餘文字 → 逐行推斷，**一行可以切成多個片段**：
     引號包住的 → speech（source = 'quoted'）
     括號包住的 → action（source = 'quoted'）
     其餘       → narration（source = 'plain'）
③ 誰說的：標記帶的 → 用它；否則 ＝ 這一則訊息的預設角色
```

**②之所以是唯一不會退化的那一層**：它**不需要模型配合**——引號與括號是中文小說的排版，
模型本來就這樣寫。長對話裡標記一定會逐漸掉光（模型模仿自己最近的輸出＝單向退化），
那時候只剩這一層撐著。

### 刻意**不做**的事（每一條都是「猜錯比不猜更糟」）

- **不猜心聲**：`（…）` 是動作不是心聲，兩者在中文裡無法可靠分辨。
- **不從散文推斷說話者**：`她說：「…」` 會切成 `narration(她說：)` ＋ `speech(「…」)`，
  但那個「她」是誰**不解釋**——用訊息本身的角色名，或標記的 `who`。
- **不做巢狀標記**：第一版沒有巢狀。要支援得寫真的 parser，那是另一個決定。
- **不解析 Markdown**：粗體、清單是**行內格式**，跟「誰在說話」無關，不要混進來。

## 5. 容錯契約（**模型走樣是常態，不是例外**）

| 情況 | 行為 | 為什麼 |
|---|---|---|
| 標記未閉合 | 吃到**下一個標記之前**，回報 `unclosed`（格式／致命） | 吃到結尾會把後面**正常閉合**的標記一起吞掉——比走樣更糟 |
| 引號未收尾 | 吃到**行尾**，回報 `unclosed-quote`（格式／可接受） | 寧可多認一段台詞，也不要讓整段文字消失 |
| 孤兒收尾標記 | 當普通文字，回報 `orphan-close`（格式／可接受） | 它通常代表前面那一段被別的東西吃掉了——走樣的第一個線索 |
| 未宣告的標記名 | 當普通文字，回報 `unknown-tag`（詞彙／可接受） | **走樣偵測的主力**：模型最常見的錯是用了別的名字 |
| 宣告成資料但內容不符 | **整塊當文字**，回報 `data-mismatch`（詞彙／可接受） | 半對的資料畫成表格比純文字更難讀 |
| 短標籤 `<n>` vs `<note>` | **不命中** | 標籤名後面必須是 `>` 或空白 |
| 空的一對引號 `「」` | 當雜訊（不是空台詞） | 不然會畫出一個空氣泡 |
| `null` / 數字 / 空字串 | 空節點樹 | 同 §7.4b 的型別：壞輸入不該讓整個面板變死格 |

**通則**：**必須可靠的東西，不能放在需要模型配合的地方。**

### 5.1 檢查結果的形狀（修復層的眼睛）

`parseMessage` 除了 `nodes` 也回傳 `problems`，**兩層、兩級、帶原文行號**：

```js
{ layer: 'format' | 'schema',        // 兩層
  severity: 'fatal' | 'acceptable',  // 兩級
  kind: 'unclosed' | 'unclosed-quote' | 'orphan-close' | 'unknown-tag' | 'data-mismatch',
  line: 16,                          // **原文行號**（1 起算）——不是 `para`
  tag: '台詞',                        // 相關的標記名（有的話）
  quote: '「' }                       // 相關的符號（有的話）
```

| 層 | 是什麼 | 修復方式 |
|---|---|---|
| **`format`** | 語法：標記有沒有成對、引號收尾 | **大部分可以在本地修**（規則就那幾種，而且機械式） |
| **`schema`** | 詞彙：`kind` 認不認得、內容符不符合約定 | **也可以本地修**：打錯的模糊比對（編輯距離 ≤ 2）、缺的用推斷反推 |

> 實測結論：**模型不需要進修復迴路。** 跑完一輪之後，「交給模型」的清單裡
> 只剩 `missing-text`——而那一種本來就沒有內容可修（沒東西可損失）。
>
> ⚠️ 而且 **`acceptable` 的那些不該佔用模型的呼叫**：它們已經降級處理過了。

| 級 | 意思 |
|---|---|
| **`fatal`** | 會影響後面的解析（未閉合會把後面吃進來）→ **值得修** |
| **`acceptable`** | 已經降級處理，不修也看得下去 → 不必修，但要**看得見** |

> **不分級的話修復會每一輪都跑**（貴又慢），而你本來只是多了一個空格。

### 5.2 修復是**例外**，不是必經

**正常的回覆：② 是空的、③ 不存在。** 如果每一則都要走到修復，那是**上游有問題**
——不是修復器不夠強。

| 症狀 | 真正該改的地方 |
|---|---|
| `bad-json` 常出現 | 提示詞太長／要求太多，模型記不住 → **縮短它** |
| `unknown-kind` 常出現 | kind 清單沒講清楚，或一次給了太多值 → 少給幾個 |
| 格式常常整個掉光 | 格式說明沒放進世界書，或位置太遠 → 放到**尾端** |
| 通通都常出現 | 這個格式對這個模型太複雜 → **簡化格式**，不是加強修復 |

> **修復率是提示詞與格式的健康指標。**
> 它的用途是「告訴你上游壞了」，不是「拿來當管線的一站」。
>
> ⚠️ 而且這一條**會影響評估**：拿一份刻意弄壞的測試資料去跑，你會以為
> 「每次都要修」。真實的評估要看**修復率**（多少比例的回合走到 ③），
> 那個數字接近 0 才是對的。

## 6. 消費者怎麼讀（同一棵樹，各自取需要的）

| 消費者 | 讀什麼 | 備註 |
|---|---|---|
| **畫面** | `line` 分組 → `kind` 上 class | 外觀由 `<酒館>/custom.css` 決定 |
| **語音** | `kind === 'speech'` 的節點，`who` 選聲音 | **預設只唸 `marked`**；`quoted` 要不要唸是使用者的選擇 |
| **統計** | 按 `kind` / `who` 計數 | |
| **匯出** | 全部節點的 `text` 接回去 | 因為 I2，原文永遠接得回來 |
| **之後的 workflow** | 見 §7 | |

**新增消費者時不要新增解析。** 讀同一棵樹——否則每加一個功能就多一套轉換邏輯。

## 7. 保留：引擎語意（**這一版不定義**）

遊戲要的「意圖／結果／狀態變化」是另一層：

```
顯示語意（本頁 §2）     給讀者：台詞、旁白、動作、資料
引擎語意（未定案）       給 workflow：intent、outcome、delta
```

**同一個節點可以兩者都有**（就是多幾個欄位）。現在**先不定義**，但兩條規則已經確定：

1. **生成要一次（不可分割），結算可以多路（事後 fan-out）。**
   多個模型同時「產生」會有一致性與順序耦合的問題；事後結算不會，而且失敗隔離。
2. **宿主半永遠只碰檔案。** 模型分流做在 Agent 面／preset——
   v1 死掉是因為宿主半跟核心服務糾纏（`CHANGELOG` 2.0.0），不是因為多模型。

## 8. 擴充規則

| 要加什麼 | 怎麼做 | 算不算破壞性 |
|---|---|---|
| 新的顯示 kind | §2 加一列 ＋ 消費者的預設行為（通常是「不唸、照文字畫」） | 否（加法） |
| 新的節點欄位 | 加欄位，**不要改既有欄位的語意** | 否 |
| 新的標記名 | 使用者在設定檔宣告（**不是**改程式） | 否 |
| **改 `text` 的語意**（例如改成「已剝掉引號」） | **不要做** | **是**——會讓所有消費者與歷史訊息的意思改變 |
| **讓 `kind` 由使用者自由發明** | **不要做** | **是**——每個消費者都要處理未知值 |

## 9. 已定案（2.6.57）與還沒定案的

> ⚠️ **這一節以前整節是「還沒定案」，而 1–4 現在都定案了。**
> 它們之所以一直是留白，有一半的原因是**沒有東西會產生它們**：這一頁 §1 寫著
> 「結構化是主線」，但**沒有任何一份提示詞告訴模型要那樣寫**——`choices`／`data`
> 節點只能由標記或結構化的一行產生，而兩者都沒被啟用。
> 2.6.57 補上了「指定」那一半（`render.json` → 提示詞）。

### 已定案

1. **設定檔的位置與名字**：`<酒館資料夾>/render.json`。
   與 `theme.json` **分開**（那個管外觀、這個管「怎麼讀訊息」，兩者改的時機不同）。
   沒有那個檔案 ⇒ 走預設（`mode: 'plain'` ＋ 內建的引號／括號／標記），
   **所以它不存在也不會壞**。實作：`lib/render.js`（正規化）＋
   `lib/workspace.js` 的 `readRender`／`writeRender`。
   ⚠️ **`writeRender` 是整份寫入、不是 patch**（同 `theme.write`）：要改一格就送完整一份。
2. **畫面**：`para` 分組與 `kind` → class 的渲染**已經接上了**（`renderMessage`）。
   多行的節點（標記區塊）畫成 `div`——`<span>` 留不住換行，那會讓「標記設對了、
   排版全亂」。
3. **`rows` 怎麼畫**：**表格 ＋ 進度條**，而進度條**只在值是帶單位的數字時**出現
   （`lib/render.js` 的 `progressOf`：只認 `62%` 與 `3/10`）。
   ⚠️ **沒有單位的數字不畫**（`好感度 62`）——我們不知道它的滿分是多少，
   而畫錯的長度比不畫更具誤導性。這是「猜錯比不畫更糟」的第二次現形。
4. **`choices` 可不可以點**：**可以，但預設不行**（`render.json` 的 `choicesClickable`）。
   點了**只填進輸入框、不送出**（送出是不可逆的：那一則會進 `.jsonl`）。
   關著的時候畫成**純文字**——不要畫成按鈕卻沒反應（欺騙性的 UI）。

### 這一頁新增的兩條契約

5. **三種模式**（`render.json` 的 `mode`）：`plain`／`marked`／`structured`。
   ⚠️ **`plain` 是預設，而且它「一個字都不加」**——那是「既有對話的行為不變」的
   實作方式（格式說明是每一輪都要付的 token，而且它會改變模型的寫法）。
   ⚠️ **只有 `marked` 模式把標記交給解析器**：`structured` 模式下模型吐了
   `<台詞>` 代表它**走樣了**，我們應該看見那些角括號（`unknown-tag` 也會回報它），
   不是默默畫成台詞。實作：`parseConfigFromRender()`，`test-render.mjs` 第 7 節釘住。
6. **`data`／`choices` 的結構化寫法**（`structured` 模式）：
   ```json
   {"kind":"data","rows":[{"key":"好感度","value":"62%"}]}
   {"kind":"choices","items":["去酒窖，順便拿燈","留下來"]}
   ```
   ⚠️ 這兩個 kind 的內容**不在 `text` 裡**（一個在 `rows`、一個在 `items`），
   所以 §3 的節點形狀裡 `text` 對它們是**衍生的**（由 rows／items 接回來，
   好讓不懂 `rows` 的消費者照樣畫得出東西——漸進增強）。
   ⚠️ 2.6.57 之前 `parseStructuredLine()` 對每一行都要求 `text` 是字串，
   所以**這兩個 kind 從第一天起就不可能解析成功**——症狀是安靜的：
   模型照著指令吐出漂亮的結構，而畫面上是一整行原始的 JSON。

### 還沒定案
