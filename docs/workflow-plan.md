# 工作樓與多人房間 計劃書（ComfyUI 式的角色管線）

> **這份文件的用途**：把「多人聊天室 ＋ 工作樓」從一句話變成可以動工的形狀。
> 這裡只寫**判斷與理由**與**格式**，實作細節等動工時再補進 `plan.md`。
>
> 如果你只有五分鐘：讀 §1、§3、§8、§9。
> 要改設計的人：§3 的每一個「判斷」都是刻意的，§10 是明確不做的。
>
> 撰寫時間：2026-09-27（macOS）。
> **2026-09-27 第二次更新**：使用者的第二句話定調了整個做法（見 §1 的第二段引文），
> 而且 **2.7.0 已經把「圖的資料層」做出來了**（§8 的 P2 前半）。
> **2026-09-28 更新**：§9 的四題有三題定案了（見 §9 的表）。

## 1. 一句話 ＋ 使用者的原話

**一間房＝一個工作樓（一張節點圖）。** 房間的成員是圖上的節點，線＝「誰的輸出餵給誰」；
使用者的一句話從 `input` 節點進入，跑完整張圖之後，由 `output` 節點把結果寫回對話。

使用者（2026-09-27）：

> 順便完成多人聊天室，就是我想建立一個工作樓的UI是綁定聊天室的，然後用線來將一個一個
> 角色串聯／並聯起來，將輸出和輸入串起來，這樣也方便我添加某些工具插件。
> 我的計劃可能是用戶輸入他的輸入，然後會經過一個工作樓，例如讓所有角色先構建心理狀態
> 思考邏輯過程，然後再交給一個統一的模型，在過程中具體碰撞出來的劇情，如果中途有什麼
> 需要做決策的就連去工具當中判定是否成功之類的，總體而言會像 comfy ui

**第二句話是最重要的設計指示**（同一天，回答「節點裡面要有什麼」時）：

> 我認為先將節點結構構建出來，我們才想裏便要有什麼可能會好一點，我們假設現在的行為
> 就已經是一個完整的工作樓，我創建房間，然後選擇了一個角色進去裏面就應該是有一個
> 預設的用戶輸入進入角色然後輸出的樓，**我們直接把它拆散就可以了**

⇒ **預設圖＝現在的行為**：

```
使用者輸入（input） → 角色（cast） → 輸出（output）
```

這一張圖跑起來與現在的單人對話**一字不差**。所以 v1 **不發明節點型別**，
§5 那張表是**以後**的樣子；v1 只有三個型別（`input`／`cast`／`output`）。

拆成三個需求：

| # | 需求 | 它其實在解什麼 |
|---|---|---|
| 1 | **多人同房** | 多個角色在同一間房裡互動（SillyTavern 的 group chat） |
| 2 | **工作樓（節點圖）** | 「角色之間怎麼碰撞」從**黑箱**變成**看得見、改得動、可以重播** |
| 3 | **工具節點** | 需要判定的地方（擲骰、成功率、條件分支）交給工具，而不是讓模型自己說「我成功了」 |

## 2. 現況：兩個缺口

### 2.1 一間房只有一個角色——**路徑就是證據**

```
chats/<角色>/<roomId>/room.json      ← 角色是路徑的第一層
chats/<角色>/<roomId>/chat.jsonl
```

`docs/storage-layout.md` §1 的配對表寫得很清楚：**房間的 id 是 `<角色>/<房間id>`**。
這不是「還沒做多人」，是**當初的形狀就裝不下第二個角色**。

好消息是**訊息層已經裝得下**：`chat.jsonl` 的每一則本來就有 `name`
（`lib/workspace.js` 讀寫都有這個欄位，SillyTavern 的格式也是這樣）。
所以「多人」要改的是**房間的成員清單**，不是訊息格式。

### 2.2 「角色之間怎麼碰撞」目前是黑箱

現在一輪對話＝**一個 session ＋ 一段提示詞**：模型自己決定誰先說話、要不要讓別人插話。
使用者要的是把這件事**攤開**：誰先想、想什麼、誰看到誰的什麼、什麼時候需要判定。

⚠️ **這裡有一個必須先講清楚的風險**：工作樓會讓**一輪對話變成 N 次模型呼叫**
（N＝角色數＋導演）。成本與延遲都會**乘以 N**。所以：

- 圖**不是每一輪都必須跑**（可以「這一輪用工作樓」／「這一輪直接回」）；
- 每個節點的輸出**要看得見**（§4.3 的 run log 就是為了這個——不然使用者只會覺得「變慢了」）；
- 「並聯」是省時間的關鍵（§6）。

## 3. 判斷（為什麼是這個形狀）

### 3.1 每一個角色＝一個 DSH session（**不自己呼叫模型**）

工作樓的「角色節點」＝對**那個角色在這一間房的 session** 送一個提示，把回覆收回來。

| 理由 | 說明 |
|---|---|
| **重用 agent 面** | 「角色卡就是系統提示」、世界書觸發、persona、回覆格式、每房設定——這些**只有 agent 面做得到**（`lib/agent.js`），而它靠的是 preset ＋ session 綁定。自己呼叫模型＝把這些全部重寫一遍 |
| **並聯是天然的** | 三個角色＝三個 session，`Promise.all` 就是並聯。不需要自己管併發 |
| **工具是現成的** | 2.6.49 的每房工具權限已經存在；「導演」那個 session 授權工具就有了 |
| **宿主半的硬規則不動** | 宿主半的 `inject` 只有 `webServer`（`verify.mjs` 釘住）。工作樓**不會**讓宿主半去碰 `llm`／`settings`／`systemPrompt` |

### 3.2 執行器放在**瀏覽器半**（v1）

「送一則訊息」現在就是瀏覽器半在做（`session.prompt` ＋ `session.follow` 逐字接回來，
`lib/client.js` 的 `ensureChatSession`／送訊息那一條路）。**工作樓一輪＝同一條路的推廣。**

- 好處：不要新增任何宿主能力；串流、用量、取消全部沿用。
- 代價：**關掉頁面就停**。這跟這個插件「按了才做、沒有背景程序」的哲學一致。
- 宿主半只多一件事：**檔案的讀寫**（`workflows/<id>.json`、run log），那是它本來就在做的事。

### 3.3 多人房間的儲存形狀：`cast` 放進 `room.json`，**路徑不變**

```jsonc
// chats/<房主>/<roomId>/room.json
{
  "cast": ["老闆娘", "酒保", "常客"],   // ← 新增。第一個是房主
  "workflow": "群像劇-01"               // ← 新增（可空＝這一房不用工作樓）
}
```

| 選項 | 判斷 |
|---|---|
| **`cast` 放 room.json，路徑仍是 `chats/<房主>/<roomId>/`** | ✅ **選這個**。路徑是**身分**，動它＝所有既有 op（`resolveRoom`、`session.bind`、資產路由）都要改；而且舊房間一個欄位都不用補 |
| 另開 `chats/群組/<roomId>/` | ❌ 保留字會跟角色卡撞名（`characters/群組.png`），而且「誰是房主」變成隱含資訊 |
| 用 `角色A+角色B/` 當資料夾名 | ❌ 成員一改（加人、換人）路徑就說謊了 |

⚠️ **房主≠唯一成員**：房主只是「這一間房掛在誰的資料夾底下」。成員名單的**真相是 `cast`**。
`cast` 少一個成員＝那個人不在這一房；`cast` 空＝舊房間，行為跟現在完全一樣。

### 3.4 導演是**獨立的 session**，而且是**唯一被授權用工具**的那一個

- 導演不是某個角色兼任（角色有自己的心理狀態，兼任會讓「演」與「導」互相污染）。
- 導演用的是一份**沒有角色卡**的 session，它的系統提示來自 `workflows/<id>.json`
  的 `director` 節點設定（agent 面**已經在讀 `room.json`**，再多讀一張圖是同一條路）。
- 「需要判定的地方接去工具」＝**導演的 session 開那個工具**（走既有的每房工具權限），
  而不是我們自己實作一套判定。圖上的 `tool` 節點只是把「什麼時候該判定」畫出來。

### 3.5 明確**不選**：宿主半自己呼叫 `llm`

代價是把 §3.1 那些東西全部重寫（卡片→系統提示、世界書、persona、回覆格式、per-room 參數），
而且宿主半多依賴一個核心服務＝**多一個讓 `dsh web` 開不起來的理由**（macOS 上發生過）。
「角色卡就是系統提示」是這個專案唯一做對角色扮演的地方，不重寫第二次。

## 4. 資料格式（三個地方）

### 4.1 `workflows/<id>.json`——圖本身

```jsonc
{
  "version": 1,
  "id": "群像劇-01",
  "name": "群像劇：先想再演",
  "nodes": [
    { "id": "in",   "type": "input",     "at": [40, 200],  "config": {} },
    { "id": "hist", "type": "history",   "at": [40, 320],  "config": { "last": 20 } },
    { "id": "a",    "type": "cast",      "at": [280, 120], "config": { "card": "老闆娘", "private": true } },
    { "id": "b",    "type": "cast",      "at": [280, 280], "config": { "card": "酒保",   "private": true } },
    { "id": "m",    "type": "merge",     "at": [520, 200], "config": { "separator": "\n\n" } },
    { "id": "d",    "type": "director",  "at": [720, 200], "config": { "temperature": 0.9, "maxTokens": 900 } },
    { "id": "dice", "type": "tool",      "at": [720, 380], "config": { "tool": "dice", "on": "d" } },
    { "id": "out",  "type": "output",    "at": [960, 200], "config": { "speakers": true } }
  ],
  "edges": [
    { "from": "in",   "to": "hist" },
    { "from": "hist", "to": "a" },
    { "from": "hist", "to": "b" },
    { "from": "a",    "to": "m" },
    { "from": "b",    "to": "m" },
    { "from": "m",    "to": "d" },
    { "from": "d",    "to": "out" }
  ]
}
```

- **人看得懂、可以手改**（跟 `room.json`／`tavern.json` 同一個原則）。
- `at` 只是畫布座標；**不影響執行**（執行只看 `edges`）。
- `id` 是給線用的，**使用者改名的時候線不會斷**。

### 4.2 `room.json` 的新鍵

| 鍵 | 什麼 | 預設 |
|---|---|---|
| `cast` | 成員的卡 id（第一個＝房主） | 空＝單人房（跟現在一樣） |
| `workflow` | 這一間房用哪一張圖 | 空＝不用工作樓 |

### 4.3 `runs/<runId>.jsonl`——**這一輪到底發生了什麼**

住在房間資料夾底下：`chats/<房主>/<roomId>/runs/<runId>.jsonl`，**一個節點一行**：

```jsonc
{"seq":1,"node":"a","type":"cast","card":"老闆娘","startedAt":"…","ms":2140,"in":"…","out":"（她的心理狀態）…","tokens":{"in":820,"out":190}}
```

三個理由，缺一不可：

1. **私有輸出要有地方住**。角色的「心理狀態」**不該**進 `chat.jsonl`（那是對話紀錄，
   使用者要能讀、能匯出、能拿去別的前端）。沒有 run log，這些中間產物就只能丟掉。
2. **「變慢了」要有解釋**。使用者看到的是「這一輪跑了 4.2 秒」；他要能看到那 4.2 秒花在哪。
3. **重播與除錯**。改了圖之後「上一輪到底吃到什麼」是唯一能對照的東西。

⚠️ run log 是**可以丟的**（跟 `session_projcache` 同一種東西）：刪掉只失去重播，不失去對話。

## 5. 節點型別（v1）

| type | 做什麼 | 主要設定 | 輸出 |
|---|---|---|---|
| `input` | 這一輪使用者的話（圖的起點） | — | 文字 |
| `history` | 這一房近 N 則對話（餵給下游當上下文） | `last`／`all` | 文字 |
| `cast` | **一個角色**：對它的 session 送提示、收回覆 | `card`、`prompt`（指令模板）、`private`（要不要公開） | 文字 |
| `merge` | 把多條線合流成一個輸入（並聯的收斂點） | `separator`、`label`（要不要標「誰說的」） | 文字 |
| `director` | **統一模型**：吃上游全部輸出，寫出劇情 | `prompt`、模型、`temperature`／`maxTokens`／`stop` | 文字（可結構化，見 §7.3） |
| `tool` | 判定：骰子／成功率／條件分支 | `tool`、`expr`、`on`（接在哪個節點之後） | 文字 ＋ `ok`（走哪一條線） |
| `output` | 寫回 `chat.jsonl` | `speakers`（要不要依 `name` 拆成多則） | — |

**為什麼 `cast` 不叫 `character`**：這間酒館的「角色」在 UI 上叫**卡司**（🎭），
節點名跟著 UI 走，使用者才不用學第二套詞。

## 6. 執行語意（這一節是工作樓的「合約」）

1. **拓撲序**：從 `input` 開始，一個節點的所有上游都完成才輪到它。
2. **同層並聯**：互不依賴的節點**同時**跑（`Promise.all`）。兩個角色節點＝同時想。
3. **沒有迴圈**（v1）：圖必須是 DAG。**有環照樣存得下去**（回傳 `errors` 給 UI），
   但**執行**會拒絕（`topoOrder` 直接回失敗）。⚠️ 設計書本來寫「存檔時就報錯」，
   動工時改掉了：編輯到一半的圖一定會經過「還不完整」的狀態，拒絕存檔＝把使用者的
   工作丟掉；而畫布上拉錯一條線就會造出環，那是最不該懲罰使用者的操作。
4. **私有 vs 公開**：**只有 `output` 節點會寫 `chat.jsonl`**。其餘節點的輸出只進 run log。
   ——這是「角色先建構心理狀態」能成立的**唯一**辦法（不然角色會把自己想的東西唸出來）。
5. **失敗策略**：節點失敗**不中斷整輪**——標記那個節點失敗、它的下游走「沒有這個輸入」，
   最後由 `output` 寫出「這一輪有 N 個節點失敗」的提示（跟現在送訊息失敗的處理同一個調性：
   告訴使用者發生什麼，而不是默默變短）。**可設定**：`onError: "skip" | "stop"`。
6. **取消**：使用者的取消＝中止所有還在跑的 session 請求（沿用送訊息那一條路的 `signal`）。
7. **重播**：按 run log 上的一輪＝把它的輸入重新餵一次（**不寫回對話**，只跑給你看）。

## 7. UI

### 7.1 放在哪

**房間頁多一個分頁「🕸️ 工作樓」**（現在是五個：💬 對話／🖼️ 插圖／⚙️ 房間／📖 藏書／📄 檔案）。

- 使用者的原話是「**綁定聊天室的**」→ 它是**這一間房**的東西，不是酒館層的全域設定。
- 酒館層（⚙️ 設定）只放一件事：**圖庫**（有哪些圖、複製一份、改名、刪除）。

### 7.2 畫布

| 元素 | 做法 |
|---|---|
| 節點卡 | 絕對定位的 `div`（`at` 就是它的座標） |
| 線 | 一層 `svg`：`<path>` 貝茲曲線（ComfyUI 就是這個形狀） |
| 拉線 | 從輸出埠 `pointerdown` → 跟著滑鼠 → 放到輸入埠 |
| 平移／縮放 | v1 只做**平移**（空白處拖曳）；縮放**不做**（要處理座標換算與線寬，先不冒這個險） |
| 執行中的節點 | 邊框發光 ＋ 一條跑動的虛線（DSH 的 `StatusDot` `ongoing` 是同一個語言） |
| 節點設定 | 點節點→右側面板（**不要用彈窗**：調圖時要一邊看圖一邊改） |

⚠️ 這一頁是**手寫的 `__ModuleLoader__` bundle、沒有 JSX、沒有 bundler**（repo 的既有約束）。
畫布是這一整個功能**最大的一塊工作量**，不是最難的一塊。

### 7.3 導演的輸出為什麼要用**既有的回覆格式**

`docs/reply-format.md` 已經定義了「模型可以吐什麼、kind 清單、節點形狀、容錯行為」，
而且 `render.json` 已經能把它變成提示詞。**導演節點直接沿用那一份契約**：

- 導演吐「誰說了什麼」→ `output` 節點的 `speakers: true` 就把它**拆成多則**寫進 `chat.jsonl`，
  每一則帶自己的 `name`（§2.1 已經確認訊息層裝得下）。
- 於是**立繪層的多人規則**（`docs/design-language.md`：「非發話者 `brightness(.62) saturate(.8)`
  ＋ `scale(.94)`」）當場就有東西可以吃——那一條規則是**為這一天先寫好的**。

## 8. 分期與測試

> 原則：**每一期都能單獨出貨、單獨測試**。不要做一個「全部做完才能用」的大改。

| 期 | 內容 | 測試 | 出貨了嗎 |
|---|---|---|---|
| **P1** | **多人房間**：`cast`、成員列、多說話者氣泡 | `test-workflow` 6d、`test-client` 9f／14n、`smoke` 11l | ✅ **2.7.0 完成**（回覆順序＝並聯，一人一則；「輪流／加權隨機」還沒做） |
| **P2** | **圖的資料層＋執行器**：`workflows` 的讀寫、DAG 驗證、拓撲執行、run log | `test-workflow.mjs`（純函式：拓撲、並聯、失敗策略）＋ `test-client` 9b–9e ＋ `smoke` 11l | ✅ **2.7.0 完成**（送訊息真的走圖了） |
| **P3** | **工作樓 UI**：畫布、拉線、節點設定、執行高亮、run log 檢視 | `test-client` 14c／14m／**14o**（畫布、拖曳、**拉線與五種不給接**、加／刪節點、存檔） | ⏳ **2.7.0 有畫布 ＋ 拉線 ＋ 加／刪節點**；**執行高亮與 run log 檢視還沒** |
| **P4** | **工具節點**：骰子、成功率、條件分支；接上每房工具權限 | `test-workflow`（判定結果走對線）＋ `test-agent`（工具授權） | ❌ |

**P1 與 P2／P3 是獨立的**：多人房間不需要工作樓就能用（ST 的群聊也沒有節點圖），
反過來工作樓也需要多人房間才有意義。

⚠️ **使用者 2026-09-27 選了「全部一起做」**（不是一期一期出貨），所以實際的順序是
**P2 先落地（2.7.0 ✅：資料層 ＋ 執行器 ＋ 送訊息改走圖）**，再往上接 P3 的畫布、
再拆出 P1 的多人房間。理由不變：資料層是所有東西的地基，而且它**不會改到既有房間的
任何行為**——現在連「送訊息」都還是同一條路，只是那條路現在是照圖跑的。

### 動工時抓到的兩個 bug（記在這裡，因為它們是這一塊的典型失敗形狀）

1. **`sendChatMessage` 只在有 `onDelta` 時才累積文字**。執行器原本「沒有人要看串流就
   不給 `onDelta`」——那會讓角色的回覆**接回來但是空的**，而畫面上一切正常（因為有
   串流）。症狀：角色明明有講話，寫進紀錄的是空的。
2. **「有上游、但上游是空的」不可以退回使用者輸入**。原本兩種情況都退回，於是一次角色
   失敗會讓 `output` 把你說的那句話**當成角色的回覆寫進紀錄**——紀錄開始說謊，
   比沒有回覆更糟。

兩個都只有「直接餵一張圖給執行器跑」才驗得出來（`test-client.mjs` 9b／9d）。
