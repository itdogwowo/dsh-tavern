# 世界書：現況與計劃（**這一份是給「還沒做的」看的**）

> 使用者：「盡量豐富他的功能，拍齊真正的酒館。」
> 這一頁把 ST 的欄位逐一盤點成三類：**已經有**／**做得到**／**DSH 架構上做不到**。
>
> ⚠️ 讀之前先知道兩件事：
> 1. **不是所有 ST 欄位都值得做**。有些是為了 ST 自己的系統（自動化、向量、persona）。
> 2. **有些是 DSH 的限制，不是懶**。做了只會多一個「調了沒反應」的欄位。

---

## 0. 現在的規則（實作在 `lib/worldbook.js`）

```
所有書的所有條目 → 同一個池子 → 排序 → 預算先到先得
```

| 步驟 | 規則 |
|---|---|
| 觸發 | `disable`／`enabled:false` 跳過；`constant:true` 直接入選；否則要 `key` 命中 |
| 次要關鍵字 | `selective` ＋ `keysecondary` ＋ `selectiveLogic`（AND_ANY 等） |
| 排序 | **`order` 由大到小**；同 `order` 時 `uid` 遞增（可重現） |
| 預算 | 先到先得；超過就**整條跳過**（不切斷），並回報 `truncated` |
| 位置 | **三個**（2.6.59 起）：角色卡前面／角色卡後面／接在最新訊息前面（**預設**）。每一本書自己選（書的 `position`），酒館層的預設是備援。⚠️ **這一格以前寫著「只有一種」**，理由是「DSH 只給使用者訊息一個槓桿」——那個理由**只對一半**，見 §2.6.59 |

## 1. 已經有

`key`／`keysecondary`／`selective`／`selectiveLogic`／`constant`／`disable`／
`content`／`order`／`uid`／`comment`

介面上可以改的：標題（`comment`）、觸發關鍵字（`key`）、常駐（`constant`）、
**優先序（`order`）**、內容（`content`）。

### `order` 的慣例

| 值 | 放什麼 |
|---|---|
| **900–999** | **每一輪都必須在**的（輸出格式） |
| 100–199 | 世界觀、人物設定的常駐條目 |
| 20–99 | 場景／關鍵字觸發 |
| 0–19 | 錦上添花 |

**為什麼重要**：世界書接在最新訊息**前面**，所以**越前面＝越靠近「現在」＝模型越容易遵守**；
而預算是先到先得，**小 `order` 的可能整條進不去**。

## 2. 做得到（照價值排序，還沒做）

### 2.1 `scanDepth`——**最值得做的一個**

**問題**：現在關鍵字**只掃這一輪進入的訊息**。所以「上一輪提過鳳梨」，
這一輪沒提，那條設定就消失了。

**做什麼**：`scanDepth: N` ＝ 掃**最近 N 則**訊息。

**代價**：`collectLore(books, scanText, options)` 現在收的是一個**字串**。
要改成收**訊息陣列**（或 `[{text}]`），並保留一個「合併成字串」的相容路徑。
**簽章會動**，所以 `lib/agent.js` 的呼叫點要一起改。

**要注意**：ST 的語意是「每條目自己的 `scanDepth`」。那代表**每條目掃不同的範圍**，
所以不能只傳一個合併字串——要傳陣列進去逐條判斷。

### 2.2 `probability` ＋ `useProbability`

**做什麼**：入選之後擲一次骰子，`probability: 60` ＝ 六成機率注入。

**代價**：很小（一個 `Math.random()`）。**但要注意可重現性**：
`collectLore` 現在是**純函式**（同樣輸入→同樣輸出，測試才寫得出來）。
加了隨機就必須**把亂數來源注入**（`options.random`），否則測試會變成擲骰子。

### 2.3 遞迴三兄弟：`excludeRecursion`／`preventRecursion`／`delayUntilRecursion`

**做什麼**：**被注入的內容本身也可以觸發別的條目**（ST 的遞迴掃描）。

**代價**：`collectLore` 外面包一層迴圈，每輪拿「這一輪新注入的內容」再掃一次，
直到沒有新命中或到達深度上限。三個旗標各自控制「這條能不能被遞迴觸發／
能不能觸發別人／要不要延到下一個遞迴層」。

**要注意**：一定要有**深度上限**（ST 預設 2～3 層）。沒有上限就是無限迴圈。

### 2.4 `group`／`groupWeight`／`groupOverride`

**做什麼**：同一組裡**只挑一個**（例如「三種天氣描述只出現一種」），
`groupWeight` 決定權重，`groupOverride` 讓這條自己決定要不無視群組。

**代價**：中等。要按 `group` 分桶、桶內加權抽一個。同樣有**可重現性**問題（見 2.2）。

### 2.5 `sticky`／`cooldown`／`delay`

**做什麼**：
- `sticky: 3` ＝ 觸發後**繼續生效 3 輪**（即使關鍵字不再出現）
- `cooldown: 5` ＝ 生效後**冷卻 5 輪**不再觸發
- `delay: 2` ＝ 命中後**延後 2 輪**才注入

**代價**：**最大的一個**。它需要「每一份對話的回合狀態」——誰在第幾輪生效過。
那不再是純函式，需要一個**側檔**（像 `.sessions/` 那樣）。

**要注意**：這是 `plan.md` R3 的鄰居（「不要自創 session 事件型別」）。
側檔可以，但**不要寫進 `.jsonl`**——那會讓 DSH 讀不懂整份對話。

### 2.6 `caseSensitive`／`matchWholeWords`

**現況**：行為是固定的（而且中文的 `\w` 問題我們已經處理過——見 `plan.md` §5 第 8 條）。

**做什麼**：照欄位走。`caseSensitive` 很便宜；`matchWholeWords` 要**維持**
「對非 ASCII 無效」那條規則（否則「酒」會在校「酒店」裡命中）。

### 2.7 per-entry `token_budget`／`ignoreBudget`

**現況**：預算是全域的。
**做什麼**：每條自己的上限，以及「這條不計入預算」。
**代價**：小，但要先想清楚**兩個預算誰先算**（全域先扣還是逐條先扣）。

### 2.8 `depth`——**能做，但要先決定代價**

**做什麼**：插在「倒數第 N 則」之前，而不是永遠接在最新那則前面。

**為什麼先不做**：**KV 快取是前綴快取**。插在中間＝那個點之後的快取全部失效
（`lib/worldbook.js` 的註解就是在講這件事）。深度的代價是**每一輪重算**。

**如果要做**：只在「這條真的需要離遠一點」時用（例如大型世界觀設定），
而且要量過 token 成本再決定。

## 3. DSH 架構上做不到（**不要做，做了只會多一個沒反應的欄位**）

| 欄位 | 為什麼 |
|---|---|
| **`position` 的八種** | ⚠️ **2.6.59 起我們有三個**（角色卡前／後、最新訊息前）。原本寫的「只有一個槓桿」**是錯的**：`ctx.systemPrompt.variable()` 的取值函式每一輪都重跑（2.6.47 的 live-reload 就是那個機制的證據），所以系統提示**也是**一個槓桿。ST 剩下的五種（對話中第 N 層、Author's Note、範例對話開頭／結尾、outlet）我們仍然沒有對應的東西可以插——我們只有「最新那一則」，沒有第 N 層 |
| `role` | 同上——我們改不了訊息的角色（只有使用者訊息這個槓桿） |
| `vectorized` | 要向量資料庫（另一套系統） |
| `automationId`／`triggers` | ST 的自動化系統 |
| `matchPersonaDescription` 那一組 | 要 persona／使用者人設系統（我們還沒做） |
| `useGroupScoring` | 隨 `group` 一起才有意義（見 2.4） |

> 這一張表跟 `plan.md` §8 的「還沒做的 / 已知限制」一致。
> **那些欄位留在檔案裡是為了可攜**（拿去 SillyTavern 用、或從那裡拿回來），
> 不是為了生效——所以**不要為它們調數值**。

## 4. 建議的實作順序

| # | 項目 | 為什麼這個順序 |
|---|---|---|
| 1 | **`scanDepth`** | 最有感：關鍵字提過之後還留著。而且它會動 `collectLore` 的簽章——**越早改越便宜** |
| 2 | `probability` | 很便宜，但會引入「亂數來源要注入」這個模式（2.4 也要用） |
| 3 | 遞迴三兄弟 | 需要在 1 的簽章改完之後才順 |
| 4 | `group` 群組互斥 | 用 2 的亂數模式 |
| 5 | `caseSensitive`／`matchWholeWords` | 獨立，隨時可做 |
| 6 | per-entry 預算 | 要先定「兩個預算誰先算」 |
| 7 | `sticky`／`cooldown`／`delay` | 最大工程（要側檔、要回合狀態），而且要先想清楚它跟 R3 的關係 |
| 8 | `depth` | 最後——要先量 KV 快取的代價 |

**每一步的規矩一樣**：先改 `lib/worldbook.js`（純函式 ＋ 測試），
再接 `lib/agent.js` 的呼叫點，最後才是介面。
