# 酒館模式的設計語言（**改 UI 之前先讀這一份**）

> 這份是**契約**，不是靈感集。每一條都有數值或規則，寫 UI 的時候照著做；
> 要偏離就在 PR 裡說明理由，順便回來改這一頁。
>
> 來源：三份研究（見 §9）。配色與對比是**實算**的（WCAG 相對亮度公式），
> 不是估的。token 的權威定義在 `lib/theme.js`。

---

## 0.0 ⚠️ 兩個區，規矩相反（**先讀這一節，不然整套會做反**）

使用者原話：

> 「**酒館街系列是應該跟從系統 DSH 的，因為他建在 DSH 當中**；我說的不同風格是指
> 具體酒館——就像酒館有不同的裝修風格一樣」

| 區 | 範圍 | 跟誰 | 憑什麼 |
|---|---|---|---|
| **側邊欄區** | 酒館街（區塊標題、酒館列、對話列、⋯ 選單）、設定 → 插件卡片 | **DSH 原生**（`--dsw-alias-*`，帶深色 fallback） | 它是 DSH 的導航。**換酒館不該換它**，切換宿主主題要跟著走 |
| **主面板區** | 大廳／包廂／卡司／藏書（`main` 面板裡面的一切） | **酒館自己的 `theme.json`**（`--dsh-tv-*`） | 「一間酒館一種裝修」。整包帶走時外觀跟著走 |

**這不是偏好，是歸屬**：掛在 DSH 上的東西跟 DSH 一致；酒館自己的空間才由酒館決定。

實測（淺色 DSH 主題 ＋ 酒館的「墨水與暖光」深色裝修）：

| | 側邊欄 | 主面板 |
|---|---|---|
| 文字 | `rgb(15,17,21)`（跟 DSH 一致） | `rgb(243,230,210)`（奶油白） |
| 底色 | 宿主決定（淺色） | `rgb(20,16,13)`（暖棕） |

**視覺上的刻意結果**：兩邊刻意不同色系——介面（導航）與場景（酒館）一眼分得開。
> 這跟 Disco Elysium 的原則一致：DE 的世界觀用自然綠／冷灰，而 **UI 資訊層刻意用
> 另一種色系**，讓介面永遠不會被讀成場景的一部分。

實作上的兩個後果：

1. **主面板區不准出現宿主的顏色變數、也不准有寫死的 hex**——全部走 `--dsh-tv-*`，
   否則 `theme.json` 換不動。**測試會分區掃**（側邊欄區要求用宿主變數、
   主面板區要求用 token）。
2. **選單 portal 到 `document.body`**，拿不到側邊欄那棵子樹的值 → `inheritTheme()`
   從**實際的 DOM 顏色**複製（`getComputedStyle` 的 `color` / `borderTopColor` /
   列的背景色）。⚠️ **不要用 `getPropertyValue('--dsw-…')`**：它回的是變數的**文字**
   （`var(--dsw-alias-label-primary,#e6e8eb)`），不是解析後的顏色。

> 所以「主題」的意義是**這間酒館的裝修**，不是整個插件的皮膚。

## 0. 一句話

**極簡的骨架、酒館的靈魂。** 平常安靜（近單色的表面階梯），
只有重要的事（角色、對話、進行中）才亮（單一暖色強調）。

**三個不准**（每一條都是從別人的錯誤學來的）：

1. **不准寫死顏色。** 元件只准用 `var(--dsh-tv-*)`。改版前有 129 處寫死的顏色、
   7 種不一致的圓角——那就是「膠水感」。測試會掃。
2. **不准用 `*` 選擇器或 `:root` 之外的洩漏。** SillyTavern 的
   `* { text-shadow: … }` 會污染整個宿主 DOM，這是前例。我們的樣式全部掛在
   `.dsh-tv-*` 類別底下。
3. **不准每個元件自己發明圓角／陰影／時長。** 圓角只有四階、陰影只有兩階、
   時長只有兩階。要第五種就先回來改契約。

## 1. 表面階梯（改版前完全沒有這個概念）

深色模式**不是靠加大陰影**拉層次，而是**把表面提亮**（M3 surface tint 的作法）。
相鄰層的亮度差約 6–10 個百分點；實作上就是四階背景：

| token | 值 | 用途 |
|---|---|---|
| `surface-0` | `#14100D` | 最底：整個面板的背景 |
| `surface-1` | `#1B1611` | 卡片：列表項、訊息列 |
| `surface-2` | `#241C16` | 浮起：輸入框、選單、hover 的列 |
| `surface-3` | `#2E241C` | 最浮：模態、被選中的卡片 |

**深色模式用底色分層，不要用大陰影**（陰影在近黑上幾乎看不見，只會變髒）。
陰影只留給「真的浮在別的東西上面」的東西（選單、模態）。

---

## 2. 文字三階

| token | 值 | 對 `surface-0` 的對比 | 用途 |
|---|---|---|---|
| `text-1` | `#F3E6D2` | **15.4:1** | 敘事正文、標題 |
| `text-2` | `#C6B199` | **9.2:1** | 次要：說明、標籤、時間 |
| `text-3` | `#9C8A74` | **5.7:1** | 最弱：提示、placeholder、停用 |

**不要純白**（`#fff` 在近黑上會 shimmer）。奶油白 `#F3E6D2` 在同等亮度下更暖、
也更適合承接角色卡的暖色插圖。

**對比規範**：一般文字 ≥ 4.5:1（WCAG 2.2 AA），內文建議 7:1（Apple HIG）。
`text-3` 只用在非必要的輔助資訊。

## 3. 強調色：只有一個

| token | 值 | 對比 | 用途 |
|---|---|---|---|
| `accent` | `#E8A33D` | **8.8:1** | 唯一強調色：主要動作、選中、角色名牌 |
| `accent-hover` | `#F5BC63` | 11.0:1 | hover |
| `accent-soft` | `rgba(232,163,61,.14)` | — | 選中列的底、標籤底 |
| `glow` | `#D98A2B` | — | 環境光（立繪後方的光池、邊光） |

**填入式按鈕的文字要用深色**：`surface-0` 壓在 `accent` 上是 **8.8:1**；
白字只有 2.2:1 ❌。這一條很容易寫錯。

**飽和色只留 1–2 個角色**（主要動作 ＋ focus）。「luxe」讀起來是克制，不是霓虹。

> 如果之後新增的主題其強調色對比偏低，要把它**拆成兩個 token**：
> `accent`（當文字用，需 ≥ 4.5:1）與 `accent-fill`（當填色用，相對背景需 ≥ 3:1）。
> 目前的預設 A 組因為強調色本身就有 8.78:1，可以共用一個值。

### ⛔ 大面積填色必須低彩度

Character.AI 2026 改版把泡泡換成「鮮豔、幾乎霓虹」的藍並溢到深色模式，
使用者回報**眼睛疲勞、頭痛（散光者尤甚）**，很多人要求「把灰色泡泡還回來」。
**M3 的官方立場也一樣**：「深色主題應避免飽和色……飽和色在深底上會產生視覺振動，
造成眼睛疲勞。」

→ **泡泡與大面積表面用低彩度**（M3 的劑量：chroma ≤ 6–8，幾乎察覺不到的色相偏移）；
**飽和色只留給小面積強調**（按鈕、選中、進行中）。

### ⛔ 硬規則：不可以移除對話流裡的角色身份標記

Character.AI 2026 改版把聊天流中的角色頭像移除，社群反彈的重點就是**沉浸感被摧毀**。
所以：訊息列的角色名牌、頭像、立繪**不是裝飾**，是「誰在說話」的錨點。
要精簡版面時，先動別的地方。

## 5. 圓角、陰影、動效、字體

### 圓角：四階，用乘數導出（不要逐處硬編）

`--dsh-tv-radius-md: 10px` 是基準，其餘是乘數：

| token | 倍率 | 值 | 用途 |
|---|---|---|---|
| `radius-sm` | ×0.6 | 6px | 標籤、小按鈕、縮圖 |
| `radius-md` | ×0.8 | 8px | 列表項、輸入框 |
| `radius-lg` | ×1 | 10px | 卡片、面板 |
| `radius-pill` | — | 999px | 膠囊按鈕 |

**同心圓規則**（Apple WWDC25）：內層圓角 = 外層 − padding。
例：外層 10px、padding 4px → 內層 6px。

### 陰影：只兩階，而且帶色相

| token | 值 | 用途 |
|---|---|---|
| `shadow-1` | `0 1px 2px rgba(0,0,0,.35)` | 列表項 |
| `shadow-2` | `0 12px 32px rgba(0,0,0,.45)` | 選單、模態 |

**不要用純黑大陰影**：純黑會同時降低飽和度。深色模式優先靠底色分層（§1）。

### 動效：只有五個動作，全部可被 `prefers-reduced-motion` 關掉

| 動作 | 時長 | 曲線 | 內容 |
|---|---|---|---|
| hover | 120ms | `ease` | 只動 `color` / `opacity` / `transform` |
| 訊息進場 | **240ms** | `cubic-bezier(.2,0,0,1)` | `opacity 0→1` ＋ `translateY(8px→0)`（>12px 就拖） |
| 表情／立繪切換 | 300ms | `ease` | **fade-through**：舊的 0→0.35 淡出、新的 0.35→1 淡入（**刻意幾乎不重疊**，比交叉淡入更不易閃爍） |
| 待機呼吸 | 4–6s | `ease-in-out alternate infinite` | `scale(1↔1.006)` |
| 場景／對話切換 | 320ms | `ease-in-out` | 黑幕 `opacity 0→1→0` |

**只動 `transform` / `opacity` / `filter`。** 不要動 `box-shadow`、漸層色停點、
`width`、`margin`、`font-size`（會觸發 layout，串流時會抖）。

### 字體：三個，不要更多

```
ui     : -apple-system, "PingFang TC", "Microsoft JhengHei", "Noto Sans TC", sans-serif
prose  : "Iowan Old Style", "Source Serif 4", "Songti TC", "Noto Serif TC", Georgia, serif
mono   : ui-monospace, SFMono-Regular, Menlo, Consolas, monospace
```

避免 Poppins / Montserrat 當主字體（AI 樣板感）。

## 6. 敘事體排版（**這是「讀小說」與「讀聊天紀錄」的分界**）

角色扮演的正文不是聊天訊息，要照**書**排：

### ⛔ 中文有兩個硬規則（違反會直接壞掉）

**1. 絕對不要用假斜體。** 中文字體**沒有斜體**，瀏覽器的「合成斜體」是人工傾斜 14°，
套在方塊字上會嚴重變形。所以：

```css
:root, .dsh-tv-view { font-synthesis: none; }   /* 直接禁止瀏覽器偽造斜體／粗體 */
```

「動作／舞台指示」改用**顏色 ＋ 字重 ＋ 括號**表達，不要用 `font-style: italic`：

```css
.dsh-tv-action { color: var(--dsh-tv-text-2); font-weight: 400; }
.dsh-tv-action::before { content: "（"; }
.dsh-tv-action::after  { content: "）"; }
```

**2. `ch` 不能用來量中文。** `70ch` 是「70 個『0』的寬度」，不是 70 個中文字。
中文行長要用 `em`：實作值 **`max-width: 34em`**（約 30–40 字）。

### 四種文字的樣式（選一套並在 UI 明示，不要混用）

| 種類 | 規則 |
|---|---|
| 敘事（旁白） | `--dsh-tv-font-reading`、15.5–17px、**`line-height: 1.8–2.0`**（中文要用 2 附近，比英文寬鬆）、**`max-width: 34em`** |
| 動作／舞台指示 | `text-2` ＋ 括號（**不用斜體**，見上） |
| 引號台詞 | `text-1`，引號用「」；可加極淡的 `accent-soft` 底色 |
| 心聲／獨白 | `text-3` ＋ 左側 2px `line` 線、`padding-left: 12px`（**同樣不用斜體**） |

- **行長是鐵則**：WCAG 1.4.8 要求 ≤ 80 字元、**CJK ≤ 40 字**。
- `text-wrap: balance` **只用在標題**（它只在 ≤6 行生效，而且對效能有影響）；
  **不要用在長訊息**。
- **不要在訊息氣泡裡用 `overflow: hidden`**（長內容會被切掉）。
- 角色名牌：12.5px、`font-weight: 600`、`letter-spacing: .04em`、`color: var(--dsh-tv-accent)`。
  全大寫才加字距（5–12%），而且**絕不套到中文**。

## 7. 材質與氛圍

### 對話框的「材質三件套」（4 行 CSS，質感差距最大）

```css
background: linear-gradient(180deg, var(--dsh-tv-surface-1), var(--dsh-tv-surface-0));
border: 1px solid var(--dsh-tv-line);
box-shadow:
  inset 0 1px 0 rgba(255,255,255,.06),   /* 上緣高光 */
  inset 0 -1px 0 rgba(0,0,0,.35),        /* 下緣暗線 */
  var(--dsh-tv-shadow-2);                /* 外部投影 */
```

顆粒（選配）：`opacity: .045; mix-blend-mode: overlay` 的 noise 疊層。
**不要用真的材質圖**（會跟文字打架）。

### 立繪（sprite）——決定「角色站在場景裡」還是「貼圖浮在 UI 上」

尺寸照 SillyTavern：高度上限 `90vh`、寬度 = 聊天欄以外的單側空間、
`object-fit: contain`、`position: absolute; bottom: 0`、`z-index` 在聊天面板**後面**。

**底部遮罩（關鍵）**：

```css
mask-image: linear-gradient(to bottom, #000 0 62%, rgba(0,0,0,.72) 78%, rgba(0,0,0,.28) 90%, transparent 100%);
```

**邊光**：

```css
filter: drop-shadow(0 8px 28px rgba(0,0,0,.5))
        drop-shadow(0 0 34px color-mix(in srgb, var(--dsh-tv-glow) 24%, transparent));
```

**多人**：非發話者 `brightness(.62) saturate(.8)` ＋ `scale(.94)`，
發話者 `brightness(1)` ＋ `translateY(-6px)`，`transition: 240ms`。

### ⚠️ 立繪與氛圍層的三個陷阱

1. **`backdrop-filter` 的 backdrop root 陷阱**（最容易「設計稿對、實作壞掉」）：
   只要「背景」與「毛玻璃面板」之間的任何一層有 `filter` / `opacity < 1` /
   `mask` / `mix-blend-mode` / 自己的 `backdrop-filter`，就會建立新的 backdrop root，
   毛玻璃**靜默失效**變成透明或純色。而氛圍設計正好需要這些（暈影、顆粒、調色層）。
   → **氛圍層放 `z-index: 0` 的獨立堆疊脈絡，對話框不要是它的子元素。**
2. **`mask-image` 只吃 HTTP(S) URL**：`file://` 會讓整個元素變全透明。
   漸層用 alpha 模式（點陣圖的 luminance 模式跨瀏覽器不可靠）。
3. **立繪的陰影只能用 `drop-shadow`**（沿 alpha 成形）；`box-shadow` 的
   `inset` / `spread` 不會沿輪廓。想要描邊就疊四向 1px `drop-shadow`。

**底部淡出用五停點**（比四停點自然）：

```css
mask-image: linear-gradient(to bottom,
  #000 0%, #000 62%, rgba(0,0,0,.85) 74%, rgba(0,0,0,.45) 86%, transparent 100%);
```

**安全區**（角色的臉不能被 UI 蓋住）：桌面臉部中心 `(30%, 30%)`、手機 `(50%, 24%)`；
文字安全區桌面自 **58% 寬**起、手機自 **42% 高**起。

**層級**：立繪 `z-index: 2`、對話框 `z-index: 3`（立繪在對話框**後面**）。

### 環境光

暖冷分離是燭光感的來源：**亮部偏琥珀、暗部偏藍紫**。
立繪後方放一個 `radial-gradient` 的光池（`filter: blur(40px)`）。
**不要**做整畫面變色（廉價，而且會讓文字對比失效）。

## 7.5 訊息流的版面架構：垂直 feed ＋ 右下角 dock

**這是有設計師一手論述支撐的架構決定，不只是偏好。** Disco Elysium 主設計師
Robert Kurvitz 的原話：

> 「如果你用電腦，**螢幕右下角是你 60% 時間都在看的地方**。畫面的重量永遠在右下角。
> 你的時鐘在那裡、你的系統匣在那裡、你的訊息在那裡。」

他的 UI 參考對象是 **Twitter**：對話做成**向上堆疊的垂直欄、「像 Twitter 一樣捲動」**，
而重要操作（對話抉擇）放在**系統通知的位置——右下角**。

```css
.chat-feed  { display: flex; flex-direction: column; }   /* 往上堆疊，新的在下面 */
.action-dock { position: absolute; right: 24px; bottom: 24px; }  /* 關鍵操作固定在右下 */
```

**配套的色彩原則**（同一份訪談）：DE 的世界觀用自然綠／冷灰，而 **UI 資訊層刻意用
一種醒目的人造亮綠色**——讓介面永遠不會被讀成場景的一部分。
→ **氛圍色（背景、立繪光）與 UI 色（強調、狀態）要是不同色系**，
否則使用者分不清「這是場景」還是「這是按鈕」。我們的 `info #7FA8C9`（冷藍在暖底上）
就是這個原則的實作。

> 另一個佐證：Baldur's Gate 3 的玩家研究（Bilkent 碩論，12 位首次玩家 think-aloud）
> 發現**派對肖像與左側面板「多數參與者從未注意」**。→ 如果一個面板沒人看，就不要做；
> 預算放在**對話流本身**與**右下角 dock**。

## 8. 串流與空狀態（我們已經有實際行為，這裡是規格）

- **串流**：用 `requestAnimationFrame` 批次 flush（token 常快於 60fps）；
  不要每個 token 重建 DOM。**只在使用者貼著底時自動滾**（離底 > 60px 就尊重他）
  ——這一條我們已經實作（40px 門檻）。
- 串流中的氣泡尾端加閃爍游標（避免被誤判「已回答完」）。
- 無障礙：容器 `role="log" aria-live="polite"`，串流中 `aria-busy="true"`，
  **絕不用 `assertive`**。
- **空狀態**：圖示 40px ＋ 標題 ＋ **最多 3 個 starter prompt**（更多會決策癱瘓），
  放在**輸入框正上方**（點擊率 3–4 倍）。**絕不顯示空白輸入框**。

## 9. 三組可選色票

`lib/theme.js` 的 `base` 只切深淺；**氛圍**靠 token 覆寫（`theme.json`）。
三組都經過對比實算：

| | 底色 | 強調 | 文字-1 | 適合 |
|---|---|---|---|---|

## 11. 已知的技術陷阱（踩過的）

- **色票只有一個來源**：`lib/theme.js`。客戶端 bundle 沒有 ESM import，
  由 `theme.read` 把 `defaults` 送過去。第一版在 client 抄了一份，改色票時兩邊立刻走散。
- **`--dsw-alias-bg-elevated` 不存在**：用它會落到 fallback，淺色主題下變成
  「深字壓深底」。portal 到 `document.body` 的選單要用 `inheritTheme()` 從側邊欄
  當下的 computed style 取色。
- **同一個 class 名不准定義兩次**：`.dsh-tv-chat` 曾經同時是「對話頁容器」與
  「側邊欄對話列」，後者的 `display:flex` 蓋不掉前者的 `flex-direction:column`
  → 對話列變成直的、元素互相重疊。測試會掃「同一個 class 被定義兩次」。
- **`event.currentTarget` 在之後的繪製時是 `null`**（React 合成事件會清掉它）。
