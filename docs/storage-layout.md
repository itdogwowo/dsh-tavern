# 儲存佈局（storage layout）

> 狀態：**已實作**（v2.3.0）。本文描述資料在磁碟上的形狀與寫入規則。
> 相關：[三份參考專案的設計判斷](design-comparison.md)

## 0. 一句話

> **一個人看的東西＝一個檔；一組圖＝一個資料夾，用同樣的 id 配對。**

資料目錄與媒體目錄**平行並排**，不互相嵌套。看到 `characters/老闆娘.json`
就能推出圖片在 `art/characters/老闆娘/`。

## 1. 為什麼不把圖塞進實體資料夾（硬限制）

最直覺的形狀是「一個角色一個資料夾，卡和圖住一起」：

```
characters/老闆娘/card.json
characters/老闆娘/images/微笑.png
```

**這個形狀會壞掉**，因為 SillyTavern 對 `characters/` 有兩個行為：

1. **子資料夾＝表情圖組（sprite folder）**——它會把 `characters/老闆娘/` 當成
   「老闆娘的表情圖組」，把裡面的插圖全部當 sprite 撿走。
2. **角色庫只列舉 `.png` 檔案**（`GET /api/characters/all`）——我們的 `card.json`
   在它眼裡**根本不存在**。

結果：**整個角色庫在 ST 裡消失，同時多出一堆莫名其妙的表情圖。**

反過來也一樣糟：如果把圖直接散在 `characters/`（`characters/老闆娘.png`），
**ST 會把每一張圖當成一個獨立的角色**列出來 → 角色庫出現一堆重複人物。

> ⚠️ **2026-09-22 更新：這一點對「PNG 卡」不成立，而且我們現在刻意用它。**
> ST 把 `characters/*.png` 當成角色**正是因為那本來就是它的角色格式**——卡片資料
> （提示詞、開場白）住在 PNG 的 tEXt chunk 裡。所以 `characters/` 底下兩種都收：
> `.json`（酒館自己的格式）與 `.png`（**PNG 卡**，見 §2b）。
> 上面那段「角色重複」講的是**插圖**被散置進去，那種情況仍然是錯的——
> 插圖一律留在 `art/`。

```
(B) 巢狀 → 角色消失      (C) 插圖散置 → 角色重複
(A) 平行目錄 ＋ characters/ 只放卡（.json 或 PNG 卡）   ← 我們選這個
```

## 2. 定稿的形狀

```
<酒館資料夾>/
├── characters/                    資料：一個實體一個檔
│   ├── 老闆娘.json
│   └── 學徒.json
├── worldbooks/
│   └── 鯨落設定.json
├── chats/                         資料：需要多檔的實體才給它一個資料夾
│   └── 老闆娘/
│       └── 初次見面.jsonl
├── art/                           媒體：與資料目錄平行
│   ├── characters/                配對 characters/<id>.json
│   │   ├── 老闆娘/
│   │   │   ├── 微笑.png
│   │   │   ├── 生氣.png
│   │   │   └── 招呼.png
│   │   └── 學徒/
│   ├── worldbooks/                配對 worldbooks/<id>.json
│   │   └── 鯨落設定/
│   │       ├── 封面.png
│   │       └── 鯨落港.png
│   ├── chats/                     房間 chats/<角色>/<房間id>/{room.json, chat.jsonl, art/}
│   │   └── 老闆娘/
│   │       └── 初次見面/
│   │           └── 店內.png
│   └── tavern/                    這間酒館自己的圖（只有一個實體，所以沒有 id 層）
│       └── 店面.png
├── tavern.json                    這間酒館的設定（含「哪一張是主圖」）
└── README.txt                     說明這個資料夾是什麼
```

### 配對表

| 實體 | 資料檔 | 它的 id | 媒體目錄 |
|---|---|---|---|
| 角色卡 | `characters/<id>.json` **或** `characters/<id>.png`（PNG 卡，見 §2b） | 檔名去副檔名 | `art/characters/<id>/` |
| 世界書 | `worldbooks/<id>.json` | 檔名去 `.json` | `art/worldbooks/<id>/` |
| 房間 | `chats/<角色>/<房間id>/chat.jsonl` | `<角色>/<房間id>` | `chats/<角色>/<房間id>/art/` |
| 店面 | （`tavern.json` 的一部分） | （無） | `art/tavern/` |

### 2b. PNG 卡（`characters/<id>.png`）——提示詞住在圖裡面

使用者（2026-09-22）：「提示詞住在 PNG 裡，我這裡指的是**酒館角色卡的寫法**」
→「PNG 卡直接就是卡（讀得到、寫得回去）」。

| 規則 | 內容 |
|---|---|
| **讀** | `characters/*.png` 直接就是卡：讀 `ccv3`（優先）或 `chara` 的 tEXt chunk。丟進去就會出現在卡司／海報牆／新對話。 |
| **寫** | 在面板上改一張 PNG 卡 → **寫回同一張 PNG**（`replaceCardInPng`：換掉舊的卡片區塊、`IDAT` 一個位元組都不動、沿用原本的關鍵字）。**不會**長出一份 `.json`。 |
| **圖** | 卡片本體**就是**這張卡的立繪（沒有插圖時頭像／海報用它，走 `/api/dsh-tavern/card/<id>`）。它不算插圖（`source: 'card'`），插圖管理器不給刪。 |
| **兩個都有時** | `.json` 優先（那是酒館自己編的那一份）——`cardFileOf()` 是唯一的判斷點。 |
| **匯入** | PNG → **位元組原封不動**存成 `characters/<id>.png`（不轉檔、不寫 `originals/`、不複製到 `art/`）；JSON → `characters/<id>.json`。**撞名自動編號**（`名字-2.png`）。 |
| **新建酒館的預設角色** | 就是出貨的 `samples/characters/老闆娘.png` 逐位元組複製。 |

⚠️ **寫回一定要用「換掉」而不是「接上去」**：讀取端 `ccv3` 優先，所以對一張已經有
`ccv3` 的圖再 `writeCardIntoPng(…, {keyword:'chara'})`，讀回來的還是**舊的 ccv3**
（改了卡、存檔看起來成功，其實沒生效）。`replaceCardInPng` 就是為此存在，
測試釘住「卡片區塊只有一個」與「非 tEXt 的位元組完全相同」。

## 3. 四個掛載點形狀完全一致——這不是巧合，是規則

四個掛載點**都是資料夾**，即使世界書或店面「通常只有一張圖」。

**不要按「通常有幾張」設計，要按「它是一個實體」設計。**

理由：猜測使用者的用法一定會錯。實際例子——原本判斷「世界書封面通常一張就夠」，
但世界書同樣會有多個場景（鯨落港、議事廳、海圖），對話室也會有房間變化，
店面也會有不同時段或角度。

形狀一致的收益：**一種規則、一組測試、一個使用者要記的事情。**
特例是要付利息的：多一種形狀就多一組判斷、多一組測試、多一個例外。

## 4. 寫入規則

### 4.1 檔案分三類，寫入規則不同

| 類別 | 檔案 | 誰寫 | 規則 |
|---|---|---|---|
| **A. 我們管理的** | `~/.dsh/taverns.json`、每間酒館的 `tavern.json`、`README.txt` | 只有我們 | **原子寫入**；`README.txt` 只在不存在時建立 |
| **B. 使用者擁有的** | `characters/*.json`、`worldbooks/*.json` | 使用者＋我們 | **原子寫入** ＋**寫之前先留一份原樣** |
| **C. 只增不改的** | `chats/**/*.jsonl`、`art/**/*` | 我們只建立、不覆蓋 | 不需要原子性（我們根本不覆蓋） |

**C 類不需要原子寫入**——這是現有設計的直接紅利：`createRoom` 用 `mkdir`（不帶 `recursive`）當獨佔鎖，
`writeAsset` 撞名自動編號（`微笑.png` → `微笑-2.png`）。**不覆蓋的檔案沒有半個檔案的風險。**

### 4.2 原子寫入是什麼

直接寫檔在磁碟上是三步：**截斷 → 寫入 → 完成**。如果行程在「截斷」與「完成」之間死掉
（斷電、被強制關閉、crash、磁碟滿），檔案就停在「被截斷、只寫了一半」——
**舊的沒了、新的也不完整**。

原子寫入改成：

```
1. 寫到旁邊的暫存檔   tavern.json.tmp-9f3a     ← 原本的檔案完全沒動
2. 寫完、flush
3. rename(暫存檔 → tavern.json)                ← 同分割區上，作業系統保證原子
```

結果：斷電時只有兩種可能——**舊的完整版本**，或**新的完整版本**。
損失的只是「這次修改沒存到」，而不是「這個檔案毀了」。

### 4.3 我們永遠不覆蓋「不是我們建立的檔案」

B 類有**兩個寫入者**（使用者和我們）。使用者可能同時用編輯器開著同一個檔。

規則：**要寫之前先確認這個檔案上次是不是我們寫的。**
不是 → **先把它另存一份**（`.original.json`），再寫。

這借自 Tauri 團隊的做法：偵測到外部改過就拒絕無聲覆蓋，但**留一份讓使用者能救回來**。
也呼應 flizzywine 的 `originals/` 精神，但**只在真的需要時才產生**，
不預先為每個檔案都複製一份。

### 4.4 碰撞一律「不覆蓋」

| 動作 | 行為 |
|---|---|
| 開新對話 | 撞名自動編號（`初次見面-2.jsonl`） |
| 上傳插圖 | 撞名自動編號（`微笑-2.png`） |
| 寫卡片／世界書 | 使用者明確給 id 才寫那個檔 |

**保持一致。** 作為對照，SillyTavern 在三個地方有三套哲學：
存檔**直接覆蓋**（最危險的那條）、改名 400 硬失敗、匯入卡片自動編號。
我們一致走「不覆蓋」，這是我們的資產。

### 4.5 實作對照（v2.3.0）

| 規則 | 實作位置 | 測試 |
|---|---|---|
| 原子寫入 | `lib/write.js` 的 `atomicWrite`（暫存檔 → rename） | `smoke.mjs` 第 13 項：**真的在寫入中 SIGKILL**，正式檔必須完好；對照組（直接寫檔）被截斷成 0 bytes |
| 獨佔建立（不覆蓋） | `lib/write.js` 的 `createExclusive` / `createUnique` | `createRoom` 用 `mkdir` 當獨佔鎖（撞到就換一個 id）、`ensure()` 不覆蓋既有設定檔 |
| B 類寫入的無損保證 | `writeCharacter` / `writeWorldbook` 只覆蓋認識的欄位 | `test-workspace.mjs` 第 10、11 項：逐欄位往返相等（含未知欄位、`extensions`、內嵌世界書、兩種世界書方言） |
| 來源圍籬 | `lib/index.js` 的 `originFenceFailure` | `smoke.mjs` 第 14 項：遠端／跨站／DNS rebinding／不同 Origin 全部擋下，正常本機請求通過 |

**所有**寫入都走 `atomicWrite`：`~/.dsh/taverns.json`、`tavern.json`、
`characters/*.json`、`worldbooks/*.json`、`art/**`。
`chats/**/*.jsonl` 只用 `createExclusive`（我們從不覆蓋對話，所以沒有原子性問題）。

**來源圍籬**（不屬於佈局，但同一批做的）：DSH 的 `webserver` **本身沒有任何來源檢查**，
而我們的 op 會建立／寫入／刪除檔案，所以兩條路由都套了四項檢查
（來源位址、`Host`、`Sec-Fetch-Site`、`Origin`）。
真的要用區網或遠端介面時設 `DSH_TAVERN_ALLOW_REMOTE=1`——放寬的是「只有本機」，
「同源」那兩項仍然有效。

### 4.6 匯入的卡片會多留一份原版

`character.import` 匯入 **PNG 卡**時，除了寫出 `characters/<id>.json`，
還會把**原始 PNG 位元組**留在：

```
<酒館>/
├── originals/cards/<id>.png      ← 原始位元組（只有 PNG 卡才有）
├── characters/<id>.json          ← 我們自己的儲存格式
└── art/characters/<id>/<id>.png  ← 同一張圖，當成這張卡的插圖
```

為什麼 PNG 要留、JSON 不用：PNG 卡除了卡片 JSON，還有**我們重建不出來的圖片位元組**
（tEXt chunk 以外的一切）。JSON 卡的文字本身就是資料，寫出去不會失真。

為什麼放 `originals/` 而不是 `characters/`：**`characters/` 是 SillyTavern 會讀的目錄**，
多放非卡片檔案會污染它的角色庫（它只列 `.png`，會把那個原版當成第二個角色）。

**同名不覆蓋**：原版的意義就是「第一次匯進來的樣子」，重複匯入不會蓋掉它。

1. **路徑一律逐段驗證**，每一段都不允許 `.`、`..`、路徑分隔符（`resolveWithin` 的精神）。
2. **顯示名 ≠ 路徑名**：使用者給的名字可以是中文、空白、emoji；進入路徑前正規化成 id。
   這是我們已經在做的分工（`assetOwner`／`normalizeAssetId`），**繼續保持**。
   （SillyTavern 正是在這一層吃過虧：它的備份 key 把非 ASCII 壓成 `_`，
   導致中日韓名字共用同一份配額，後來要加 sha256 尾綴才修好。）
3. **不引入索引檔**。資料夾內容就是真相——這是不建 manifest、不建 index.json 的理由。
   唯一的中介資料是 `tavern.json` 裡的「哪一張是主圖」，因為那是**設定**，不是清單。

## 6. 已定案（2026-09-17）

1. **不做「外部改過」偵測。** 使用者確認「同時用編輯器開著同一個檔」不是真實情境，
   所以不引入任何變更偵測機制（不存 hash、不加中繼資料）。
2. **不做 `.original.json`。** 承上——沒有偵測就沒有「該不該留原版」的判斷依據。
   B 類檔案的保障改為**規則 + 測試**，而不是多一份檔案：
   - 寫卡片／世界書一律走「讀出既有 JSON → 只覆蓋我們認識的欄位 → 寫回」，
     **未知欄位原樣保留**。
   - 這條規則用**無損往返測試**釘住：拿真實格式的卡（含未知欄位、`extensions`、
     `character_book`）寫入再讀出，**語意必須逐欄位相等**。
   - 「原樣保留」若真的失败，那是 bug，要用測試抓，不是用備份檔掩蓋。
3. **`~/.dsh/taverns.json` 不額外備份。** 它壞掉的代價是「酒館清單要重新加回來」，
   而資料本身都在各自的酒館資料夾裡。與其多一份備份，不如**在寫入時就套用原子寫入**
   （見 4.2），讓它不容易壞。

> 三條的共通邏輯：**能靠「寫入時就做對」解決的，就不要靠「壞掉之後再補救」。**
> 備份是補救，原子寫入是防範；規則加測試是防範，`.original` 是補救。

## 7. 可以之後再說的（不影響上面）

- **`art` 這個名字**：它同時裝立繪、場景、店面圖，語意有點模糊。
  改成 `media/` 或 `assets/` 更準，但 `art` 已經在程式碼、README 與既有資料夾裡了，
  改＝多一次遷移。**建議不改**，這是低價值高風險的改動。
- **快取／索引**：目前 `tavern.list` 與 `character.list` 是 O(N) 掃描。
  規模大了會慢，但任何快取都會製造「第二份真相」。
  真的遇到痛點時，先做的是「清單只回主圖、縮圖按需載入」，而不是建索引檔。
